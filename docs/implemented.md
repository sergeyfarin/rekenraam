# Implemented Features

This is the feature ledger: what Rekenraam actually ships today, by area, with
backend and UI status tracked separately. It replaces the per-step trackers
(`transaction-table-plan.md`, `phase-1-implementation-plan.md`,
`setup-auth-implementation-plan.md`, `fx-refresh-implementation-plan.md`) as the
single answer to "what is done."

- **Source of truth for "what's next":** `docs/roadmap.md`.
- **Source of truth for product intent and phase boundaries:**
  `docs/product-requirements.md`.
- **Technical debt and polish:**
  [GitHub Issues](https://github.com/sergeyfarin/rekenraam/issues), with local
  IDs mapped in `docs/backlog.md`.
- **Documentation map:** `docs/README.md`.

Status legend: ✅ shipped · 🟡 backend only (no UI) · 🟦 partial · ⬜ not started.

The unused `v0.1.0` candidate baseline is in
`backend/migrations/0001_initial_schema.sql`. Its checksum is enforced, but
ADR 0013 permits an explicitly declared redesign before any installed release;
each rewrite updates the checksum, fixtures and upgrade/equivalence tests.
After the first installed release, schema changes use forward migrations.

Last documentation reconciliation: 2026-09-28 (R16 runtime extraction,
foundation, exact trade economics and correction sub-slices 4a–4u). R12a closed 2026-08-30; ADR 0012
governs the journal/subledger boundary and ADR 0013 the R16 operation model.

Replay guard on the accepted time step; wrong codes spend the same 5-in-15 throttle budget as wrong passwords; enrol/disable/regenerate each re-confirm the password. A pending enrolment never gates a login. |

## Reconciliation (Phase 3) — ✅ Core workflow shipped

| Capability | Status | Notes |
|---|---|---|
| Reconciliation sessions, checkpoints, finish/void | ✅ | `app/reconciliation.go`; API + UI. |
| Period-scoped reconciliation guard (edit/void/restore/move) | ✅ | Wired across all mutation paths; balance assertion enforced in DB tx. |
| Optimistic version guard on lifecycle writes | ✅ | T-94 (2026-09-13). An update, void, unvoid or soft-delete names the transaction version its spec and checkpoint candidates were prepared against, and the write transaction refuses to apply them to any other version — so a prepared edit cannot land on top of someone else's newer, reconciled one. A missing version is refused too. Surfaces as HTTP 409 `TRANSACTION_VERSION_STALE`; ordinary metadata edits against the current version still need no override. Approve is exempt and says why. |
| Input-independent cost-basis allocation | ✅ | T-103 (2026-09-20). A partial disposal splits a lot's or a pool's basis at the cost commodity's own maximum scale — one scale per position, resolved per command, backing off only as far as int64 projection columns require and never below a scale already recorded. Before this the split happened at whichever scale a purchase was typed at, so the same 10 EUR allocated 3, 3.33 or 3.3333 to one of three shares depending on the spelling. Truncating division, residual conservation and the immutability of acquisition and disposal evidence are unchanged; a partial disposal's basis and gain are now reported at that allocation scale. |
| Prepared writes bound to the facts they were prepared from | ✅ | T-94 / T-100 (2026-09-13). A draft promotion names the version its spec was read from, so an edit landing between `PostTransaction`'s read and `UpdateTransaction`'s own is refused instead of posting the older dates behind a live checkpoint; a promotion that names no version is refused too. A prepared posting likewise names the accounts its eligibility checks read, and the write transaction refuses it if one has been restructured since — closed in both directions, because the account write re-asks "does this account have postings?" inside its own transaction. Surfaces as HTTP 409 `POSTING_ACCOUNT_VERSION_STALE`. |
| Investment plans bound to the account versions their roles read | ✅ | T-100, second window (2026-09-19). A buy, sell, write-off, dividend or reinvestment records the account version each role check read, and the journal preparation that follows adds to the same record without displacing it — so the write refuses a command whose holding or settlement account stopped being what the plan decided it was. Without it a buy could commit a ten-share lot against an account that was no longer a holding account. |
| Reconciliation-impact preview (named-checkpoint warnings) | ✅ | Shared resolution now returns the complete unique active checkpoint set the write invalidates, including later checkpoints, with each boundary’s own statement metadata and earliest triggering entry date (T-127 #142). Commit rechecks inside its write transaction. Each checkpoint is tested against its own date/sequence boundary on every create, edit, lifecycle and posting-move path, so a same-day posting after an earlier checkpoint leaves it active and a reorder across any earlier boundary needs override (T-120 #135): `TestSameDayPostingAfterEarlierCheckpointPreservesIt`, `TestEditAndVoidAfterEarlierSameDayCheckpointPreserveIt`, `TestPostingMoveAcrossEarlierSameDayCheckpointRequiresOverride`. ## Budgets (R8)

R8 ships an exact monthly planned-versus-actual workflow at `/app/budgets`.
Targets are audited book-wide facts keyed by calendar month, posting category,
and currency. Actuals include only posted, current, non-deleted category
postings whose journal entry touches an account treated as `on_budget` on that
entry date; drafts, voids, recurring assumptions, forecasts and learned
estimates never enter the calculation. Income credits are presented as positive
magnitudes, expenses preserve their debit-positive sign, refunds may make a net
actual negative, and all target/actual/remaining arithmetic uses exact
coefficient strings in Go.

Account budget treatment is a dedicated effective-dated version history with
`on_budget`, `off_budget`, and `excluded`, separate from account kind. The
authenticated composed `GET /api/v1/budgets/month` read model returns category
rows, separately typed income/expense currency totals, currency options and the
account-treatment editor in one request. Target and treatment `PUT` operations
write their audit event atomically. Unlike currencies are never summed or
converted, and R8 deliberately has no rollover or envelope allocator. The
responsive screen has loading, empty, error and success states and copy in all
six locales. `docs/plans/budgets-plan.md` is the shipped contract.

Online import (R7) is fully shipped for Trading 212 (Slices 1–4b: connections,
fetch, durable worker, online batch flow, scheduled auto-refresh, investment
lot import — see "Online Connections" above, `docs/plans/trading212-import-plan.md`).

### Gains precision and range admission (2026-09-20)

Gains-summary monetary values use currency-labelled standard display precision;
share quantities and detailed lot values retain exact precision. Totals are
aggregated before display rounding. Same-day sales render independently, and
unrealized position keys distinguish cost currencies. Investment acquisitions
and disposals atomically reject a resulting cost-basis projection outside its
exact int64 range, preserving the journal, lots and audit on rejection (T-104).

and the supported-range limitation.

As of 2026-09-26, investment monetary coefficients cross JSON as exact decimal
strings in requests, lots, positions, previews, and gains (T-107). The backend

converting coefficients to `Number`.
