## Why the recommendation changed

1. **The original review found two different failures.** A transaction validated on one owner-local day could return the account label from the next day (#608). An account rename could fail with the clock held still because an unchanged institution had since been archived (#602). Requiring a user to pick a date for a typo invited a third problem. Editors showed today’s values while the server filled omitted fields from the chosen past version (#568). A single rule for ordinary renames looked attractive. [#608](https://github.com/sergeyfarin/rekenraam/issues/608) · [#602](https://github.com/sergeyfarin/rekenraam/issues/602) · [#568](https://github.com/sergeyfarin/rekenraam/issues/568)
2. **The first proposal and independent review favored a storage change.** A single current value would give every live reader the same name. The reviewer found a real obstacle to that promise. Transactions store the payee name resolved at entry and index that text. Renaming the linked payee alone cannot make both names searchable. The proposal grew to cover institutions, payees and search, account and category labels, category regrouping, and instrument display. It kept financial versions and proposed selected before/after values for investigation. The original and reviewed drafts remain available. [First proposal](https://github.com/sergeyfarin/rekenraam/commit/70bb5bf23c3e6ad0a4948693ed8d96827bba16b1) · [Withdrawn ADR text](https://github.com/sergeyfarin/rekenraam/blob/02a0de9bcb667729f61fbf0b9c7185260f377eb2/docs/adrs/0022-current-reference-data-and-descriptive-audit.md)
3. **The other agent subsequently narrowed its recommendation.** Tracing callers showed that many live paths already resolve today’s version. It withdrew its earlier argument that the number of version lookups justified moving every name. It also withdrew the claim that account/category work had to beat the migration freeze. Its disposable, fully migrated SQLite probe could drop the tested descriptive account columns individually and the institution/payee version tables. Migration 0002 had replaced the trigger it initially thought read category metadata. This established that the schema operations were feasible on that baseline. A data-preserving upgrade with real consumers is a separate test. The agent then proposed making reference edits effective today while keeping the tables, with report labels and payee search decided separately. [Current-reader survey](owner-current-reference-2026-10-22.md) · [Replacement trigger](../../backend/migrations/0002_category_version_delete_guard.sql)
4. **The owner raised cases where both proposals lose something.** A bank can renumber a continuing account. A fund can change its official name or ticker midyear. A user may learn about either change months later, while reconciling an old statement. An immediate-only edit can assign the wrong historical date. A current-only name plus a database audit can retain the old text yet leave it inaccessible to the person searching. Equally, an effective date adds little to correcting a spelling mistake or changing an entry suggestion. Household testing will show which tasks matter enough to support.

### What the June experiment actually changed

The 8 June experiment replaced account, institution, payee and commodity versions **and** transaction and posting versions with current records and centralized audit targets/changes. Reconciliation sessions and checkpoints switched from references to particular posting versions to references to postings. It also added an audit read API and removed reference-version routes. The prototype was preserved on an archive branch. The commit and its backup do not record the owner’s reason for setting it aside. An early reviewer could only find a local copy; the archive and commit are now publicly retrievable. [Experiment diff](https://github.com/sergeyfarin/rekenraam/commit/d01680e8135c2b454179f6282aaf7648d758c788) · [Archived branch](https://github.com/sergeyfarin/rekenraam/tree/archive/experiment-remove-versions-2026-06)

That distinction matters when revisiting this PR. The November proposal kept transaction versions, lot evidence and reconciliation links. The cheaper November alternative kept every version table. June illustrates the consequences of changing what a checkpoint identifies. It gives no measure of the cost or value of changing one label lookup. Any case for revisiting financial versions belongs in a separate decision with its own financial evidence.

## What the app already does

| Workflow | Evidence at the reviewed revision | Why it affects the choice |
|---|---|---|
| Account in a transaction or account search | Posting enrichment reads a stable account ID and resolves display fields on the owner day. The account list searches the current name, code, kind and role. It does not search past last-four hints. [Transaction service](../../backend/internal/app/transactions_service.go) · [Account repository](../../backend/internal/db/accounts.go) | Retaining versions does not make them discoverable. A search over the existing history could solve a recognition problem without copying account details onto each posting. A matching last four can identify several candidates. |
| Account or category in a report | The ledger query selects name, code **and** dated structure as of the supplied date. Spending resolves category names for its API, then the screen prefers today’s catalog label when available. Its CSV uses that same screen label. Spending groups direct category postings. [Ledger query](../../backend/internal/db/ledger.go) · [Spending service](../../backend/internal/app/reports.go) · [Screen and CSV](../../frontend/src/lib/reports/spending-view.svelte) | A label fix could be confined to a report. Switching the whole join to today would risk changing eligibility or grouping. A hierarchy-based budget subtotal can move when a category changes parent even when the direct spending and overall total agree. |
| Payee on entry, search and forecast | Linked entry records the resolved payee name alongside its identity. Free text can remain unlinked. Transaction search indexes recorded text. Forecast passes its resolved as-of date for payee enrichment. [Transaction validation](../../backend/internal/app/transactions_validate.go) · [Search index](../../backend/migrations/0001_initial_schema.sql) · [Forecast](../../backend/internal/db/forecast.go) | Distinguish the name recorded on the transaction, raw statement text where available and the linked payee’s current name. A historical search hit must not relink an old payment to a different merchant that now uses the name. |
| Saved investment output and filing copies | Saved gains, statement and returns runs retain their output payloads and fingerprints. Coverage of human labels depends on the payload and renderer. A downloaded Spending CSV contains the label rendered at export. [Investment documents](../plans/investment-reporting-plan.md) · [Saved returns](../plans/investment-returns-plan.md) | Reopening a saved document, rerunning a past period with later corrections, and finding a file previously submitted are three different requests. Compare the actual saved fields and visible labels. A hash alone cannot supply omitted wording. |

## Routes available after testing

| Route | What it would solve | Cost or failure case | Evidence that would favor it |
|---|---|---|---|
| Keep the current design and fix individual defects | Preserves late corrections, past identities and the single version model. | Historical editors still need to show the chosen period correctly wherever that workflow is promised. Name overlap remains a product question. | The household uses historical corrections, or existing workflows suffice once the proven bugs are fixed. |
| Make ordinary edits immediate and retain versions | Removes date selection and historical-form merges for the fields chosen. Technical change can be limited to those writers, forms and API validation. | A November entry cannot represent a real July change if every edit takes effect today. Storing a new version also keeps old note contents. | People repeatedly encounter the date picker for nicknames or defaults and can identify any fields that still need real-world effective dates. |
| Keep storage and fix one reader, search or import mapping | Can show a current nickname in the register, a report-end name on the year-end balance, or a former identifier in search. An alias can lead back to one stable ID. | An alias has ambiguous matches and possible reuse. Import matching and search need separate rules. A change to a shared account query reaches several reports. | An old statement or merchant repeatedly cannot be found, or one report needs a label different from the current screen. Reproduce through that entry point. |
| Retain a report or published export | Preserves the figures, headings and grouping actually delivered for that period. Later corrections can still yield an updated report. | A saved file cannot answer a different query, recover an omitted identifier or search the register. A built-in archive adds storage, export and restore obligations. | The owner can identify a particular report that must be reproduced as filed and show what is missing from the existing export or saved run. |
| Archive the old identity and create a new one | Gives genuinely separate accounts, mandates or instruments distinct activity and clear opening/closing boundaries. | Splitting one continuing account for a renumbering fragments reconciliation, transfers and performance history. A new category can split budgets and comparisons. | The underlying account or holding really changed, or the owner deliberately wants separate series. A label change alone is weak evidence. |
| Move selected fields to current records, with selective audit (withdrawn ADR) | One authoritative current description. Ordinary renames could propagate across all live views. Old names or links could still be investigated in the database. | Changes storage, writers, APIs, exports, deletion guards and tests. The audit still cannot serve in-app search or guarantee filed wording. Current grouping may change a past subtotal. | Several independent workflows demonstrably need the same current value, existing versions or narrower fixes cannot reasonably supply it, and the user accepts the historical consequences. |

The three field policies discussed were **effective-dated value**, **current value only**, and **current value plus investigation audit**. The last policy was deliberately narrow. Under the withdrawn design the event’s existing `metadata_json` would hold the subject kind/ID and changed field names. Rename values would be captured. A category move or payee default would capture both old and new targets’ IDs and display names as plain values so unused former targets could be deleted. A note, icon or website would contribute only the field name. In that design an overwritten value would be recoverable only from a backup containing it. Existing version rows can retain old contents. The owner excluded an app reader, new audit columns and indexes. “Formerly” remains an untracked idea. ## How competitors handle the same tasks

Official product documentation reviewed on 20 November 2026. The middle column describes observable behavior. The last column gives the inference for Rekenraam. These sources establish neither the competitors’ internal schemas nor a universal policy for historical reporting. [Broader competitor review](../competitor-comparison.md)

| Product and task | Documented behavior | Implication for the decision |
|---|---|---|
| KMyMoney · fix a payee name | A rename changes the displayed payee on all its transactions. When merging payees, the user may add the old names to the surviving payee’s matching list. [Payees handbook](https://docs.kde.org/trunk_kf6/en/kmymoney/kmymoney/details.payees.html) | There is a concrete precedent for correcting a typo once and separately retaining names useful to import. The matching-list behavior is documented for a merge. It establishes no automatic historical-search promise on every rename. |
| Actual Budget · match a merchant and suggest a category | Imported names can be matched to a managed payee via editable rules. A default category can then be applied on a matched import. [Payee management](https://actualbudget.org/docs/transactions/payees/) | A household may care about recognizing the next bank line more than reconstructing a former default. Test the next suggestion and check that the earlier booked category still explains the prior report. |
| PocketSmith · rename a category used by a feed | A renamed feed/file category can map future imports carrying the old label to the new category. Users can remove the mapping. [Category mapping](https://learn.pocketsmith.com/categories/6a6X8SseDAwp484bSBSH1L/editing--deleting-categories/6a6X8SseDBZYRfK9UTdjDL) | If re-import creates duplicate categories, that is evidence for a source mapping. It says little about how the previous year’s spending tree should render. |
| GnuCash · rerun or retain a report | The user can save a report configuration and rerun it. Export and print preserve a particular rendering outside that configuration. [Report window](https://www.gnucash.org/docs/v5/C/gnucash-manual/gui-report.html) | Ask whether the owner wants to rerun the same query with corrected data or retrieve the original output. Compare the two files before designing an archive. |
| Portfolio Performance · identify a security in an export | Account transaction exports carry security name, ticker, ISIN and WKN alongside amounts and dates. The manual also documents distinct security master-data and quote exports. [Export fields](https://help.portfolio-performance.info/en/reference/file/export/) | A broker statement may need an identifiable instrument as well as an amount. The documented field list does not say which historical name a regenerated export uses. Verify that separately before claiming parity. |

## What to learn from using the app

These are prompts for the household run. Record a case when it occurs. A short synthetic reconstruction is enough for #611. Keep actual statements, account hints and household amounts private. Completing this matrix is optional for #336.

| Household task | Observation that distinguishes the routes |
|---|---|
| Trace a December transfer that arrives in savings in January after the sending bank renumbers the account. | Try finding both legs using the old last four. Note whether the owner needed the December 31 closing balance and account details, or the year’s movements with each leg’s date and account. Include two possible matches. A renumbering preserves the account’s identity; opening a replacement account may warrant two. |
| Reconcile a broker statement after a July fund rebrand first learned about in November. | Try the old statement name or ticker, then the current one. Check whether the same holding, units and basis are identifiable on each date. Compare with an actual exchange into another instrument, which has its own accounting consequences. |
| Rename a merchant and change its default from groceries to household supplies. | Search by the statement text and the familiar name. Check the next suggested category and last year’s posted category. Include another merchant that later reuses the name. Count unique transaction hits and check their payee IDs. |
| Move childcare from Household to Family after keeping last year’s report. | Compare saved wording with a freshly generated report and a hierarchy-based subtotal. Record whether the owner wanted to compare both years under today’s categories or reproduce the original tree. Verify the total and underlying postings separately. |
| Correct a nickname typo, remove a private note, or encounter an archived institution on an old account. | Does a date choice help? Is the old text needed by a person using the app, by someone investigating the database, or by nobody? Can the owner correct the nickname while keeping its valid old institution link? Record any refusal separately from the desired retention policy. |

## Decision after testing

1. **Record what changed since this review.** Put the candidate SHA, relevant issue/PR or changed reader, and status of the household database on #611. For each encountered case capture the task, expected and observed result, workaround and whether it recurred. Identify the relevant date (posting day, report end, effective date of a real change, or date the output was saved). For example, finding a fund under its old ticker and seeing its old name on a filed statement are two independent outcomes.
2. **Choose the smallest route that answers the observation.** If the household completed its tasks and the existing model is acceptable, record that and resolve the holds on #568/#569 individually. For a gap, name the field, caller, intended behavior and a regression that would distinguish success from today’s behavior. Record what would still need historical meaning. Recheck competitor behavior only if the choice relies on it and the cited product has changed.
3. **If storage is still the problem, reopen the existing design evidence.** Trace every affected writer, reader, export, search and import matcher, plus the account and institution versions endpoints and token clients. Recheck future-effective and same-day versions, archive/reassign/restore races, former payee defaults, former category parents and financial foreign keys. A migration must deliberately choose the intended state when a future-effective row exists and when a late-entered correction belongs to an older interval. Prove backup, restore and upgrade for a supported book. Keep posted facts, reconciliation evidence, valuation cutoffs and saved outputs covered.
