Store these fields for the economic event time
occurred_date (DATE, required)
The date the user/bank considers the transaction happened for reporting (what shows on the statement, what user picked).

occurred_at_utc (TIMESTAMP UTC, nullable)
Exact instant if known (bank timestamp, card authorization time, etc.). Null for manual/date-only entries.

occurred_tz (TEXT IANA tz, nullable or required when occurred_at_utc is set)
The time zone that should be used when displaying the local time-of-day for that transaction (e.g. America/New_York). This is key to avoiding “I moved and my transaction changed day” surprises.

Optionally:

occurred_precision enum: date vs datetime (or infer: if occurred_at_utc is null ⇒ date-only)
source enum: manual, bank_import, etc.
Store these fields for ledger/audit time
posted_at_utc (TIMESTAMP UTC, required once posted)
When it was committed to the immutable ledger (system clock). Used for “what did my books look like as of moment T?”
This gives you:

Correct period reporting (use occurred_date)
Correct ordering and audit (use posted_at_utc)
Optional intraday sorting when available (use occurred_at_utc)
How to avoid “time zone change shifts the date”
This is the core issue you raised. Here’s the rule:

The reporting date should not depend on the viewer’s current time zone
If you compute the date as date(occurred_at_utc in viewer_tz), then moving time zones can change the date. That’s usually undesirable in accounting.

So: treat occurred_date as authoritative for period grouping, regardless of user moves.

For date-only entries: occurred_date is all you have; it never shifts.
For datetime entries: still keep occurred_date fixed to the “statement date” / “local date at origin”, and display the time using occurred_tz (or show both).
What to set occurred_date to when you import a timestamp?
When a bank provides a timestamp, you typically also get a posting date on the statement. Best options:

If the bank provides an explicit posting/transaction date: use that as occurred_date.
If only a timestamp is provided with a known time zone: compute local date in that same zone and store it as occurred_date.
If timestamp is provided but time zone is unclear (common): treat it cautiously:
store occurred_at_utc if you trust it’s UTC, otherwise store it as local-time-with-zone if possible, or drop to date-only.
Crucial: Once stored, don’t recompute occurred_date based on the user’s current zone.

Display policy (suggested)
When showing a transaction:

Always show occurred_date prominently (this is what affects month/year totals).
If occurred_at_utc is not null:
show time-of-day in occurred_tz if available (e.g. “23:30 (New York)”)
optionally allow a user preference: show also in “current time zone” as secondary info.
This avoids confusion and preserves the accounting meaning.

Sorting policy (important)
For lists you’ll want stable behavior:

Primary sort: occurred_date (DATE)
Secondary sort:
if occurred_at_utc present: sort by it
else: keep stable insertion order or use posted_at_utc
This way date-only items don’t jump around unpredictably.

Reporting queries (what to use)
Period reports (month/year, budgets, taxes): group/filter by occurred_date
“As-of moment” ledger snapshot: filter by posted_at_utc
Intraday analytics: use occurred_at_utc when available, but don’t let it redefine the date buckets unless user explicitly chooses “group by local day in current tz”.
Why this is “best”
It matches real-world expectations:

Statement date is stable and doesn’t change because you traveled.
Exact times (when known) are preserved and still useful.
Sync later is safe: UTC instants and posted timestamps are unambiguous.
